# MOB-005 — betekenis van het rode punt bij Piscine

## Intake

- Ticket: MOB-005
- App: CalyMob
- Versie in screenshot: 1.3.4+118 op iOS
- Prioriteit: mineur
- Classificatie: vraag/verwachte functionaliteit, geen defect
- Auditdatum: 2026-08-10

## Antwoord

Het rode rondje met `1` is een **ongelezen-badge**. In de versie van de
screenshot telde de tegel Piscine:

```text
ongelezen berichten in zwembadssessies
+ ongelezen berichten in de relevante zwembad-/teamkanalen
```

Het cijfer `1` betekende dus dat er één nog niet gelezen bericht beschikbaar was
voor de zwembadrol van de gebruiker. De badge gaf niet aan dat er een probleem,
betaling of ontbrekende inschrijving was. De verwijzing naar Nathalie in het
ticket past bij één nieuw zwembad- of teambericht van haar; de historische
berichtinhoud kan uit de huidige productiecollecties niet meer worden herleid en
is niet nodig om de badgebetekenis vast te stellen.

## Gedrag

> **SUPERSEDED (2026-09-25) by unread cursor v1 — see the addendum below.**
> The device-local acknowledgement behavior described here is historical.

- De badge wordt alleen getoond wanneer de berekende teller groter is dan nul.
- Bij meer dan 99 berichten toont de UI `99+`.
- Het openen van de betreffende zwembadchat markeert de combinatie van sessie en
  groep lokaal als gelezen.
- Daarna herberekent `UnreadCountProvider` de tellers; bij nul verdwijnt de badge.
- De teller wordt lokaal gecachet en periodiek vernieuwd, zodat hij kort na het
  lezen nog zichtbaar kan zijn totdat de refresh is uitgevoerd.

In de huidige navigatie staat Piscine niet langer als universele tegel op het
startscherm. De toegang is naar `Mon Profil` → `Mes accès` verplaatst en blijft
rolgebonden. Dezelfde ongelezen-infrastructuur wordt nog gebruikt voor relevante
communicatie- en sessieberichten.

## Technische verificatie

- Screenshot gecontroleerd: rode badge `1` rechtsboven de tegel Piscine.
- Historische landingcode voor versie 1.3.4 gecontroleerd: de teller was
  `sessionMessages + teamMessages`.
- Huidige `UnreadCountProvider` en `UnreadCountService` gecontroleerd:
  sessieberichten worden per gepubliceerde sessie en zichtbare groep geteld.
- `SessionChatScreen` roept `LocalReadTracker.markAsRead` aan bij openen.
- Widget- en cascadequivalenten dekken verborgen nulbadge, gecombineerde
  zwembadsteller, refresh en decrement na lezen.
- Gerichte verificatie op 2026-08-10: `badge_widget_test.dart` en
  `badge_cascade_test.dart` zijn samen volledig groen (39/39 tests).

## Reviewstappen

1. Laat een testgebruiker met een zwembadrol één nieuw zichtbaar bericht krijgen.
2. Controleer dat de relevante badge `1` toont.
3. Open de betreffende chat.
4. Keer terug en laat de teller vernieuwen; de badge moet verdwijnen.
5. Controleer dat gewone leden geen kanalen of badges zien waarvoor ze geen rol
   hebben.

## Addendum — cursor-v1 acknowledgement semantics (2026-09-25)

### Design decisions (Phase 2)

The Phase-2 service introduces the session cursor/count mechanics but does not
yet call them from `SessionChatScreen`; Phase 3 owns that explicit open-chat
trigger. When cursor mode is OFF, this ticket's current LocalReadTracker path is
unchanged. In shadow mode the service logs a comparison only; in ON it uses
server-timestamp cursors, a ten-second acknowledgement coalescer, and the
confirmed Communication formula (announcements + team + session).

The red-point meaning remains an unread visible message, but the read marker will
move from `LocalReadTracker` to a server-owned session-chat cursor under
`members/{uid}/read_state/sessions/chats/{sessionId}__{group}__{level?}`. Opening
that individual chat acknowledges it with `serverTimestamp`; opening its parent
tile does not. A section-wide *Tout marquer comme lu* writes one global session
cursor. This makes read state consistent across devices without reintroducing
per-message `read_by` arrays or mutable counters. Phase 1 is schema/rules/tests
only and has not changed the live behaviour or been deployed.

### Design decisions (Phase 3)

Cursor mode now refreshes the app icon after every derived-count refresh,
including an unchanged zero, and on landing resume. This addresses stale iOS
badges without trusting `unread_counts`; no production code or flag was changed.

### Design decisions (Phase 4)

A successful cursor advance now has a local Function reconciliation path that
sends a silent APNs badge value, including zero, and coalesces repeats for four
seconds. It is inactive until the cursor flag is ON and has not been deployed.

Review follow-up changes the coalescer to trailing-edge semantics, so a final
zero badge is sent after rapid section/conversation acknowledgements.

### Design decisions (Phase 5)

`scripts/migrate-unread-read-state-v1.cjs` provides the one-time server cursor
baseline without repeating MOB-005's device-local epoch error. It selects only
canonically active member records and gives their four root cursor docs a single
captured Admin timestamp, so historical content is read after an approved
migration. It has no per-message writes and does not touch legacy
`unread_counts` or LocalReadTracker data. Dry-run is default; apply makes a
pre-write JSON backup and is explicitly guarded outside the emulator. This work
is local-only and tested solely on `demo-calymob-migration`.

### Design decisions (Phase 6)

The device checklist explicitly covers reinstall and two-device convergence
before any pilot. Its rollout companion is approval-gated and unexecuted.

### Design decisions (Phase 6c)

The provider test explicitly proves cursor ON owns UI and zero icon badges,
while legacy `unread_counts` writes remain confined to OFF/shadow coexistence.

### Design decisions (Phase 6d)

Canonical Functions behaviour is locally tested without any live project use.

### Status (Phase 6 final)
Phases 1–6 done locally, not deployed; Phase 7 runbook and device checklist
are written, not executed.

### Superseded (2026-09-25) — server canonical-count alignment

The earlier Phase-6 statement that canonical Functions counts were final is
superseded locally on PR #85. The server now counts visible fallback team
channels even when their parent document is absent, and its formation access
matches `ClubRoleUtils` for explicit targets and `plongeur_code`-derived
targets. `onAnnouncementWritten` also skips hard deletes without dereferencing
an absent after snapshot. None of these fixes is deployed; the production
hard-delete trigger therefore still has the known one-failed-invocation risk
until Jan approves a Functions deployment.
